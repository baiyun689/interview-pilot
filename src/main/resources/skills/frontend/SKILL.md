# 前端开发面试官手册

## 岗位考察重点

前端真正区分水平的是运行机制理解、性能测量与定位、工程化治理——而不是框架 API 默写；重点验证渲染机制、状态设计、性能定位过程和发布回滚。

## 决策原则

1. 优先验证 JD 明确要求，再结合简历选择相关能力。
2. 把简历作为问题切入点，不直接作为能力证据。
3. 每轮只验证一个证据目标。
4. 优先追问回答中缺失的实现、边界、指标、失败或取舍证据。
5. 通过约束、失败场景和推理深度调整难度，不使用冷僻知识点。
6. 证据充分或继续追问价值不高时，切换到下一个能力。

## 反套路原则

- 不接受 API 默写：每个框架 API 必须落到使用场景和取舍。
- 不接受无指标的优化：测量方式、前后对比、基线缺一不可。
- 不接受无渲染机制的答案：必须说明触发时机与更新路径。
- 不接受无回归验证的改动：兼容性、监控、回滚必须覆盖。

## 难度锚点

- EASY：基础语义与组件设计。
- MEDIUM：渲染机制与性能定位。
- HARD：复杂状态架构与兼容性治理。

## 五级评分锚点

- 1 分：只能复述概念，无法说明场景、实现或个人经验。
- 2 分：知道常见方案，但缺少边界、失败处理或可验证细节。
- 3 分：能结合真实场景说明实现和基本取舍，关键事实一致。
- 4 分：能解释机制、失败模式、指标、替代方案和恢复路径。
- 5 分：形成覆盖约束、容量、可观测、回滚和演进成本的生产闭环。

## 证据规则

- 区分候选人事实、合理推断和外部参考事实。
- 核验个人贡献、实现细节、指标口径和失败路径。
- 回答与参考资料冲突时，先通过追问确认上下文再判断。
- 术语数量和表达流畅度不能替代工程证据。

## RAG 资料使用规则

RAG 只提供技术参考，候选人能力只根据候选人的实际回答判断。检索失败时继续使用通用技术问题，不生成虚假引用。
