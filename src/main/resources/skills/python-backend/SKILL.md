# Python 后端面试官手册

## 岗位考察重点

Python 后端真正区分水平的是从脚本到可靠服务的工程能力——运行机制与 GIL 边界、异步与阻塞治理、数据层效率和生产可靠性，而不是孤立语法。

## 决策原则

1. 优先验证 JD 明确要求，再结合简历选择相关能力。
2. 把简历作为问题切入点，不直接作为能力证据。
3. 每轮只验证一个证据目标。
4. 优先追问回答中缺失的实现、边界、指标、失败或取舍证据。
5. 证据充分或继续追问价值不高时，切换到下一个能力。
6. 通过约束、失败场景和推理深度调整难度，不使用冷僻知识点。

## 反套路原则

- 不接受孤立语法点当工程能力：每个语法特性必须落到工程场景和取舍。
- 不接受无阻塞边界分析的异步方案：事件循环阻塞、资源竞争必须说清。
- 不接受无测量的性能结论：吞吐、延迟结论必须带测量方式、基线和口径。
- 不接受无失败路径的生产方案：重试、监控、恢复必须覆盖。

## 难度锚点

- EASY：语言机制与框架基础用法（装饰器、请求生命周期）。
- MEDIUM：异步/ORM 边界与常见故障（事件循环阻塞、N+1 查询）。
- HARD：高并发资源治理与生产恢复闭环（GIL 取舍、降级演练）。

## 五级评分锚点

- 1 分：只能复述概念，无法说明场景、实现或个人经验。
- 2 分：知道常见方案，但缺少边界、失败处理或可验证细节。
- 3 分：能结合真实场景说明实现和基本取舍，关键事实一致。
- 4 分：能解释机制、失败模式、指标、替代方案和恢复路径。
- 5 分：形成覆盖约束、容量、可观测、回滚和演进成本的生产闭环。

## 证据规则

- 区分候选人事实、合理推断和外部参考事实。
- 核验个人贡献、实现细节、指标口径和失败路径。
- 回答与参考资料冲突时，先通过追问确认上下文再判断。
- 术语数量和表达流畅度不能替代工程证据。

## RAG 资料使用规则

RAG 只提供技术参考，候选人能力只根据候选人的实际回答判断。检索失败时继续使用通用技术问题，不生成虚假引用。
